# ASA — умный подбор event-подрядчиков (HackAlem #79-lite)

Заказчик указывает город, дату, тип мероприятия, категорию подрядчика и бюджет.
Сервис возвращает **до трёх подрядчиков из каталога и для каждого конкретное объяснение, почему он здесь и чем отличается от соседних карточек**.
Занятые на дату, дороже бюджета и не берущие этот формат в выдачу не попадают никогда.

## Запуск

Нужен Python 3.10+.

```powershell
pip install -r requirements.txt
python -m streamlit run app.py        # веб-интерфейс: http://localhost:8501
```

Без интерфейса:

```powershell
python demo.py                        # 9 демо-сценариев + имитация сбоя LLM в терминале
python -m unittest                    # 21 тест: модули команды + сквозные проверки Definition of Done
```

Модули подбора и объяснений (`matching.py`, `explanations.py`, `comparison.py`, `service.py`) работают только на стандартной библиотеке Python. Streamlit нужен только для интерфейса.

## Что происходит внутри

```
запрос ─► matching.recommend ─► comparison ─► explanations ─► app.py / demo.py
          │                     │              │
          │ 1. пул: город +     │ 4. что       │ 5. текст из подтверждённых фактов;
          │    категория        │    отличает  │    LLM (опционально) только выбирает,
          │ 2. жёсткие фильтры  │    карточку  │    какие факты подчеркнуть;
          │ 3. ранжирование,    │    от других │    при любой ошибке используется
          │    top-3, факты     │              │    детерминированный fallback
```

**1. Пул.** Подрядчики нужного города, у которых среди категорий есть запрошенная. Площадки лежат в том же каталоге: «Банкетный зал|Отель|Ресторан» находится по запросу «Банкетный зал».

**2. Жёсткие фильтры.** Кандидат исключается, если он занят на дату (`busy_dates`), его цена «от» выше бюджета, он не берёт этот формат или запрошенная длительность больше его `max_hours`. Пустой `max_hours` (флористы, декор, сувениры) длительность не ограничивает. Каждая причина считается отдельно, и из счётчиков строится сообщение.

**3. Ранжирование.** Прошедшие фильтры получают баллы: база 70 плюс прозрачные компоненты (`score_parts`, видны в интерфейсе).

| Компонента | Баллы | Смысл |
|---|---|---|
| `specialization` | 0–10 | формат стоит первым в профиле → это основное направление (10 / 6 / 2) |
| `description` | 0–10 | описание говорит об этом виде событий: «свадеб», «невест», «форум»… |
| `language` | 0–5 | совпал запрошенный язык (язык — сигнал, не фильтр) |
| `duration` | 0–5 | длительность подтверждена данными `max_hours` |

Цена баллов не добавляет: дешевле не значит лучше. При равенстве сортировка идёт по `id`, поэтому один и тот же запрос всегда даёт один и тот же порядок.

**4. Сравнение (`comparison.py`).** Для каждой карточки ищется то, что есть только у неё среди показанных: самая низкая цена, единственный язык, формат указан первым, максимальная длительность, узкая специализация. Так выполняется требование DoD «сотри имена — карточки нельзя перепутать».

**5. Объяснение (`explanations.py`).** Текст собирается **только из подтверждённых фактов** с `id`: `compare`, `profile` (дословная выдержка из описания), `format`, `available`, `budget`, `language`, `duration`, `synthetic`, `city_imputed`. Сначала идёт то, что отличает карточку, затем общие проверки. Опциональный LLM выбирает `evidence_ids`, а текст всё равно собирается локально, поэтому модель не может выдумать цену, дату или заслугу. Таймаут, ошибка API, битый JSON или недопустимый id дают fallback (`reason_source = "fallback"`).

### Три исхода

| `status` | Когда | Что видит пользователь |
|---|---|---|
| `matched` | есть хотя бы один подходящий | карточки; если меньше трёх, объясняется почему («заняты на 19 декабря — 9…») |
| `category_not_found` | в городе нет такой категории | сообщение и города, где категория есть |
| `no_match` | кандидаты есть, но никто не прошёл | счётчики причин и ближайшая свободная дата, если мешает только календарь |

### Честность данных

- `price_from_kzt` — цена «от», поэтому в тексте «цена от … укладывается в бюджет», а не «стоит».
- `price_imputed` и `city_imputed` (проставлены при подготовке датасета) показываются бейджами и в тексте («оценочная цена»).
- 13 синтетических профилей помечены зелёным бейджем, и их объяснение начинается со слов «Синтетический профиль для демонстрации».

Все проверены на реальном каталоге (`demo_scenarios.py`, тест `test_integration.py`) и доступны в интерфейсе в списке «Готовый демо-сценарий».

| # | Запрос | Результат |
|---|---|---|
| 1 | Ведущий · Алматы · свадьба · 15.10 · 1 000 000 ₸ | 3 карточки, разные баллы и разные отличия |
| 2 | То же, 19.12 | 1 карточка; «заняты на 19 декабря — 9» |
| 3 | Фотограф · корпоратив · 15.10 · 600 000 ₸ | 2 карточки: «самая низкая цена» и «дольше всех на площадке» |
| 4 | Банкетный зал · свадьба · 14.11 · 3 500 000 ₸ | площадки; синтетический профиль помечен |
| 5–6 | Флорист · свадьба · 18.10 и 17.10 | редкая категория: соседние даты дают разных флористов |
| 7 | Банкетный зал · 06.12 | `no_match`: все 7 заняты, подсказана ближайшая свободная дата |
| 8 | Флорист · Астана · той | `no_match`: не берёт этот формат |
| 9 | Лайв-бэнд · Астана | `category_not_found`: есть в Алматы |

Проверка сбоя LLM: переключатель «Имитировать сбой LLM» в интерфейсе или сценарий 10 в `python demo.py`. Объяснения остаются, источник меняется на `fallback`. Переключатель «Показать кухню» показывает баллы, использованные факты (✅) и счётчики отказов.

## Опциональный LLM

Без ключа всегда работает детерминированный fallback. Чтобы модель выбирала, какие подтверждённые факты подчеркнуть, задайте переменную окружения `OPENAI_API_KEY` (модель: `OPENAI_MODEL`, по умолчанию `gpt-4o-mini`). Используется OpenAI Responses API со структурированным JSON. Модель видит факты одного кандидата и возвращает только `evidence_ids`, таймаут 2,5 с на карточку. Ключ хранится в окружении, не в репозитории.

## Контракт

Запрос: `city`, `date` (`YYYY-MM-DD`, 23.09–31.12.2026), `event_format`, `category`, `budget_kzt` (целое ≥ 0); опционально `duration_hours` (целое > 0) и `language`.

Ответ: `status`, `message`, `counts` (`category_candidates`, `busy`, `over_budget`, `format`, `duration`, `price_missing`; один кандидат может попасть в несколько счётчиков), `elapsed_ms` и `results[]`. Каждая карточка содержит атрибуты профиля, `score`, `score_parts`, `facts[]` (`{id, text}`), `reason`, `reason_source` (`llm` | `fallback`) и `evidence_ids`.
